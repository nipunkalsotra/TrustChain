## Defects requiring attention

1. **Verification and reset emails open 404 pages.** The actual verification email links to `/verify-email/{token}`; the frontend implements `/auth/verify-email/{token}`. Reset email links to `/reset-password/{token}`; the frontend implements `/auth/reset-password/{token}`. Both were followed in Playwright and returned HTTP 404. New users cannot complete verification through the emailed link, blocking key management and invitations; password recovery is also broken through its email link. Source: [email templates](../backend/notifications/templates.py), [verification page](../frontend/app/auth/verify-email/[token]/page.tsx), [reset page](../frontend/app/auth/reset-password/[token]/page.tsx).

2. **Concurrent SDK registration loses transactions.** With one UI-created key, four simultaneous independent registrations returned one successful receipt and three HTTP 502 errors. API logs recorded `nonce too low`. Sequential registration passed. The identity writer independently reads the pending nonce before building each transaction; the observed result is consistent with concurrent calls reusing that nonce. Score writes and the anchor worker also use the configured signer, so concurrency across those paths needs review. Source: [identity writer](../backend/blockchain/identity_writer.py), [score writer](../backend/blockchain/score_writer.py). The evidence directly confirms registration failures; the broader impact on score writes is a code-based concern, not a separately proven failure in this audit.

3. **Fact-checking fails inside otherwise completed pipelines.** The successful pipeline logged `[Validator] MCP fact_check error: 'list' object has no attribute 'get'`. The validator assumes a mapping response and calls `.get()` on the adapter result. It falls back after the exception, allowing the report to complete with incomplete verification. A completed report should not be interpreted as a successful external fact check. Source: [validator](../backend/agents/validator.py), especially the MCP result handling around lines 87–107.

4. **The installed frontend dependency graph has critical audit findings.** npm reports Next.js and `proxy-addr` as critical entries. The production-only audit still reports 18 affected entries, so the findings are not confined to test tools. These are scanner classifications and affected-version findings, not proof that every advisory is exploitable through this application's routes. Review the saved audit details and update affected dependencies before production sign-off; do not apply a forced dependency rewrite without compatibility testing.

5. **The anchors page reports an unavailable pipeline chain while V2 proofs are working.** The live chain returned chain ID 31337 and confirmed audit transactions, while the frontend displayed `Pipeline chain: Unavailable`. `/chain-status` reads the legacy V1 bridge and `MONAD_RPC_URL`; the local pipeline uses `V2_RPC_URL`. V1 signing is unconfigured in this environment, so the V1-derived indicator does not describe the working V2 evidence chain. Source: [chain-status endpoint](../backend/main.py), [anchors UI](../frontend/components/product/Evidence.tsx).

6. **The anchors page overflows a phone viewport with real data.** At a 390-pixel viewport, document width was 411 pixels. The other ten workspace pages in the real-data mobile sweep fit the viewport. The fixture-based mobile checks passed, which is why the real-data check is retained as a regression. See [real mobile anchors screenshot](audits/2026-11-11/live-mobile-anchors.png).

The concurrent model-heavy test runs also exhausted Groq's 8,000-token-per-minute allowance, causing HTTP 429 errors and failed runs. Running the pipeline on its own passed. This is an observed capacity constraint; the passing retry does not demonstrate reliability under concurrent model workloads.

Source inspection also found alert and notification-preference email links pointing to `/alerts/{id}` and `/settings/notifications`, while the current workspace routes are under `/dashboard`. Those links deserve follow-up; external alert-email navigation was not a separately executed browser scenario in this audit.

## Limits of this conclusion

This is a local integration audit, not a production deployment certification. External email delivery, public RPC/testnet reliability, TLS and production cookie configuration, optional evidence publishing/IPFS, optional LangChain adapters in a separate application, other browser engines, and CI's alternate runtime versions were not independently validated. Evidence publishing was disabled in the audit configuration.

Backend skips were the container stop/recovery chaos scenario, a placeholder on-chain root-mismatch integration test, and a missing-boto3 branch that cannot run when boto3 is installed. The Python SDK skip was the score check for a run that failed under provider rate limiting. None of these skips is counted as a pass.

Production sign-off requires correcting the confirmed defects and rerunning their retained regression tests, then validating the actual deployment and its external services.
